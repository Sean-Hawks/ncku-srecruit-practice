# 序列通訊與封包：雙方怎麼解讀同一串 bytes

[← 回考場筆記入口](../README.md) · [位元運算](位元運算.md)

**串口送的是 bytes，不會自動附上「這是一張圖、一個整數、完整一包」的意思。** 雙方必須約定長度、型別、排列與邊界。

ROS topic 有自己的訊息格式；USB／UART 要由題目提供的 host／橋接程式轉接。板子插上電腦不會自動變成 ROS node。

## 文字、binary、endian

| 要表達什麼 | 實際 bytes |
|---|---|
| 文字 `"21\n"` | 32 31 0A（十六進位） |
| uint32 的 21，little-endian | 15 00 00 00 |
| 0x12345678，little-endian | 78 56 34 12 |
| 0x12345678，big-endian | 12 34 56 78 |

binary 可減少大量數值的轉換與傳輸成本；小數字未必比文字短。兩端必須一起改格式，不能只把發送端改成 binary。

## Python struct 對照：已解讀範例

假設協定是「request ID、value，各 unsigned 32-bit，little-endian」：

```python
packet = struct.pack("<II", 7, 21)  # 需 import struct
# bytes: 07 00 00 00 15 00 00 00，共 8 bytes
request_id, value = struct.unpack("<II", packet)
# request_id=7；value=21
```

| 格式字元 | 意思 |
|---|---|
| `<` | little-endian、標準大小、不加原生 padding |
| `>` | big-endian、標準大小、不加原生 padding |
| `I`／`i` | 4-byte 無號／有號整數 |
| `f` | 4-byte float，前提是協定指定此格式 |

這是解釋格式的例子，正式封包欄位以題目為準。直接把 C struct 記憶體送出去可能含 padding，型別大小與 endian 也要核對。

## 為什麼 read(8) 可能只收到 3 bytes

資料可以分次到達，read 也可能因 timeout 提早返回。接收者要累積到完整長度，再解析；例如先收到 3，再收到 5，才合成 8。

| 要檢查 | 作用 |
|---|---|
| header／magic 或固定邊界規則 | 找到一筆的起點 |
| length | 知道 payload 有幾 bytes |
| 型別與 endian | 把 bytes 還原成正確數值 |
| job_id／request_id | 結果對應哪一筆輸入，處理亂序 |
| 校驗、timeout、錯誤回應 | 按題目規定處理損壞與失聯 |

「收滿長度」不等於「已找到正確邊界」；若混入開機文字或少了一個 byte，仍可能需要重新同步。重送前也要確認如何處理重複 job_id。

## 查連線：在能看見板子的主機／指定環境

```bash
ls /dev/serial/by-id/
ls /dev/ttyUSB* /dev/ttyACM*
```

by-id 不一定存在。ttyACM0 的數字可能在重插後改變，多板優先記錄裝置序號／實際對應。

有預裝 pySerial 時：

```bash
python3 -m serial.tools.list_ports
python3 -m serial.tools.miniterm "<實際port>" "<指定baud>"
```

miniterm 用 Ctrl+] 退出。baud 要按題目設定。monitor 和正式接收程式若同時讀同一串口，可能互相讀走資料。

## 症狀對照

| 症狀 | 常見原因 |
|---|---|
| 數值看起來變超大 | endian、signed／unsigned、型別寬度錯 |
| 第一筆對、之後全部錯位 | 長度算錯、漏 byte、文字混進 binary |
| 多板答案順序錯 | 依回來順序排列，沒有按 job_id 還原 |
| 有時讀不到 | timeout、程式未啟動、開 port 觸發重啟、其他 reader |
| 主機可見、容器不可見 | 裝置映射／權限，查 [Docker](Docker.md) |

debug log 與答案通道分開；binary 中混入 printf 會改變資料內容與長度。
