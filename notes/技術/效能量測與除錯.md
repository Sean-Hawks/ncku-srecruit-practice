# 效能與除錯

[← 回考場入口](../README.md)

**先保留正確答案，再找整條路最慢的一段。** 相同測資、筆數與編譯設定比較，不能靠少算資料換速度。

## 慢在哪裡，改哪裡

| 量到的瓶頸 | 候選改法 |
|---|---|
| 格式轉換／傳輸 | binary、批次、減少往返，兩端配套 |
| 算法／推論 | 改算法、適合的位元操作、獨立工作分工 |
| 鎖等待 | 只保護必要共享狀態，移出獨立耗時工作 |
| 複製資料 | 減少重複複製，適合時用 DMA |
| 接腳時序／位元流 | 規格適合才用 PIO |

整批時間包含接收、解析、計算、搬運、等待、回傳。**非同步工作要等完成再停表**，只量 start 會低估。

## 已提供工具時的查法

| 目的 | 查閱方式 |
|---|---|
| Linux 程式總耗時 | `time ./app`，換成實際執行檔 |
| Python 某段耗時 | 前後取 `time.perf_counter()`，差值乘1000為毫秒 |
| C 編譯警告 | `-Wall -Wextra` |
| 主機 C 越界／部分未定義行為 | 支援時用 `-fsanitize=address,undefined -g`，只供查錯，量速度用正常版本 |
| GDB | `break main`、`run`、`next`、`step`、`print 變數`、`backtrace` |

`time` 的 real 是經過時間，user/sys 是累積 CPU 時間；ROS topic hz 是觀察到的頻率，不是端到端延遲。sanitizer 不證明沒有 data race；板子除錯另需現場 probe／server。

## 錯誤先分層

| 症狀 | 先查 |
|---|---|
| 編不過 | 第一個錯誤、include／工具鏈／連結 |
| 沒輸出 | 入口、輸入是否到、卡在哪個等待條件 |
| 固定算錯 | 型別、單位、endian、規格版本、核心算法 |
| 偶爾錯／崩潰 | 越界、未等完成、共享資料、buffer 提早重用 |
| 越開 worker 越慢 | 通訊成本、鎖、記憶體頻寬、工作分配不均 |

修改紀錄只需：固定輸入、答案是否一致、相同條件的耗時、這次改哪一段。時間波動大時重測幾次，看中位數與範圍。

來源：[Python 計時](https://docs.python.org/3/library/time.html#time.perf_counter)、[GCC sanitizer](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html)、[GDB](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Continuing-and-Stepping.html)。
