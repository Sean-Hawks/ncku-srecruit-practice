# 效能量測與除錯：先證明算對，再找最慢的步驟

[← 回考場筆記入口](../README.md)


**一次只改一件事，用相同輸入比結果與時間。** 印少一點、跳過運算卻答案錯，不算優化。

## 整條路分段看

```text
接收 → 解析 → 傳到板子 → 運算 → 回傳 → 發布
```

| 慢在哪 | 候選改法 |
|---|---|
| 解析／格式轉換 | 減少反覆字串轉換，按規格打包 |
| 傳輸 | 批次收送、減少往返；兩端一起改協定 |
| 運算 | 演算法、適合的位元運算、多核心分工 |
| 鎖等待 | 保護必要共享資料，移出不必鎖的工作 |
| 搬運 | 減少複製、適合時用 DMA；算進設定與等待成本 |

這些是候選，需要量測；不要一次全改。

## 命令列：Linux，有對應工具才用

下面的 ./app 是已編好的程式，要換實際路徑：

```bash
time ./app
ps -eo pid,comm,pcpu,pmem,args
```

`time` 的 real 是實際經過時間；user/sys 是累積 CPU 時間，多 thread 時可超過 real。ROS 的 `topic hz` 是觀察者收到的頻率，不等於整條系統的延遲。

重複測三次、保留每次數字，比中位數與變動範圍。固定輸入、編譯選項、工作量；不要把 Python 啟動時間當成單次 callback 時間。

## Python 分段計時

放在**實際處理函式前後**，不要包進「等下一筆訊息」的時間：

```python
import time

start = time.perf_counter()
answer = process(data)  # 換成題目實際的運算函式與資料
elapsed_ms = (time.perf_counter() - start) * 1000
print(f"compute_ms={elapsed_ms:.3f}")
```

這是片段，process/data 需先存在。非同步工作要等完成再停計時；只量 start 呼叫會低估。

## C 越界：先開警告，必要時加 sanitizer

在**Linux 有支援的編譯器與 runtime**，以你的 main.c 為例：

```bash
cc -std=c11 -O1 -g -Wall -Wextra \
  -fsanitize=address,undefined -fno-omit-frame-pointer main.c -o app-check
./app-check
```

ASan/UBSan 可幫忙找越界、部分未定義行為；不能證明沒有 thread race。多 thread 可另外用支援平台上的 `-fsanitize=thread -pthread`，不要和 address sanitizer 同時開。這些工具會改變效能，**量速度用正常版本**。

## 已裝 GDB 才用

```bash
cc -O0 -g main.c -o app-debug
gdb ./app-debug
```

GDB 內：

```text
break main
run
next
step
print x
backtrace
continue
quit
```

next 通常不進函式，step 可進函式；print 的 x 要換目前作用域裡存在的變數。板子除錯需要對應 probe／server，不直接拿主機 gdb 當已連上板子。

## 每次修改只留下這四行紀錄

```text
輸入：固定測資與筆數
正確性：與標準版本逐筆比較
耗時：三次結果、相同編譯設定
修改：只改哪個瓶頸，是否更快
```

來源：[Python perf_counter](https://docs.python.org/3/library/time.html#time.perf_counter)、[GCC instrumentation](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html)、[GDB stepping](https://sourceware.org/gdb/current/onlinedocs/gdb.html/Continuing-and-Stepping.html)。
