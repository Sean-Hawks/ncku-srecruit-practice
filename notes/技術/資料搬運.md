# 資料搬運：填工作單，交給引擎

**搬運引擎需要知道：從哪讀、往哪寫、幾筆、每筆多大、位址要不要前進。** 設定工作單並不會立刻複製資料。

## 跑現有範例

在**容器**：

```bash
cd /demo/section2-3
make run-transfer-engine
make mistake
```

檔案：[main.c](../../demo/section2-3/transfer-engine/main.c) 決定工作、[engine.h](../../demo/section2-3/transfer-engine/engine.h) 宣告介面、[engine.c](../../demo/section2-3/transfer-engine/engine.c) 實作搬運。

目前 N=8；PDF 的原版 N=4096。輸出的 spins 是主程式等待期間轉了幾圈，不是搬了幾筆，也不是吞吐量。

## 最關鍵的單位

| 欄位 | 8 個 uint32_t 的複製 |
|---|---|
| count：幾筆 | 8 |
| size：每筆 bytes | XFER_32，也就是 4 |
| 總 bytes | 8 × 4 = 32 |
| src_increment | true，下一筆讀下一格 |
| dst_increment | true，下一筆寫下一格 |

```c
job.count = N;                    // 對：N 筆
// job.count = N * sizeof(uint32_t); // 錯：把 bytes 當成筆數
```

`sizeof(uint32_t)` 在這個 8-bit byte 平台是 4。32 是 bits、4 是 bytes，單位不能混。

`make mistake` 故意把 count=32、size=4，所以搬 128 bytes。它預留較大的陣列，展示超過原本預定 8 筆的效果；實際配置只有 8 筆時，這種錯法會越界。

## 複製、填值差在哪

```text
複製：src[0] → dst[0]，src[1] → dst[1]，src[2] → dst[2]
填值：pattern → dst[0]，pattern → dst[1]，pattern → dst[2]
```

| 任務 | src_increment | dst_increment |
|---|---|---|
| 複製陣列 | true | true |
| 同一 pattern 填整段 | false | true |
| 每次寫同一硬體暫存器 | 視來源而定 | false |

硬體周邊可能還需要 DREQ 節奏控制，不是任意用 false 就能正確傳。

## 實作：填 64 筆 16-bit 的 0x1234

在**repo 根目錄**另存 `transfer_fill.c`。這題使用 repo 的模擬 API，不是 Pico SDK DMA API。

```c
#include <assert.h>
#include <stdint.h>
#include <stdio.h>
#include "engine.h"

int main(void) {
    uint16_t pattern = 0x1234;
    uint16_t dst[64] = {0};
    int ch = engine_claim();
    if (ch < 0) return 1;
    engine_job_t job = {
        .src = &pattern, .dst = dst,
        .count = 64, .size = XFER_16,
        .src_increment = false, .dst_increment = true
    };
    engine_configure(ch, &job);
    engine_start(ch);
    engine_wait(ch);                    // 完成後才能讀 dst、讓 pattern 離開作用域
    for (size_t i = 0; i < 64; ++i)
        assert(dst[i] == 0x1234);
    engine_release(ch);
    puts("64 words OK, 128 bytes");
}
```

在**repo 根目錄**編譯：

```bash
cc -std=c11 -O2 -Wall -Wextra -pthread \
  -I demo/section2-3/transfer-engine \
  transfer_fill.c demo/section2-3/transfer-engine/engine.c -o transfer_fill
./transfer_fill
```

預期 `64 words OK, 128 bytes`。改 pattern 時，assert 預期值也要改。

## 為什麼不用 dst=src 或自己寫迴圈

- 陣列不能在宣告後用 `dst=src` 整體賦值。
- 指標 `p=src` 只讓 p 指向 src，沒有複製內容。
- `memcpy(dst, src, N * sizeof src[0])` 確實複製內容，而且第三參數要 bytes。
- 目前 engine.c 也是另一條 CPU thread 跑搬運迴圈，並沒有憑空省掉 CPU。
- 真 DMA 是硬體操作匯流排；CPU 可以處理其他事，但仍有設定、同步與頻寬成本。

## 真 DMA 對照：查 API，不直接換名字

Pico SDK 常見流程：

```text
dma_claim_unused_channel
→ dma_channel_get_default_config
→ channel_config_set_transfer_data_size / read_increment / write_increment
→ dma_channel_configure
→ dma_channel_wait_for_finish_blocking
→ dma_channel_unclaim
```

configure 的**寫入位址在讀取位址前面**，要看宣告；RP2350 count 還涉及模式編碼，依 SDK／datasheet，不能直接假設和這份模擬 struct 完全相同。記憶體對齊、buffer 長度、buffer 生命週期與通道歸還都要確認。

原模擬引擎用 volatile busy，沒有完整跨 thread 同步；即使外層直接 wait，原引擎內部仍會讀 busy。這個實作題驗證設定與輸出，不代表已修好引擎的 thread safety，也不把 busy 當正式同步範本。
