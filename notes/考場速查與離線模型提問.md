# 考場速查與離線模型提問

用瀏覽器頁內搜尋找 `ROS`、`mask`、`count`、`鎖`、`PIO`、`模型`。這頁保存可重用的小片段；實際平台、版本、允許工具與提交方式依現場說明。

## ROS 沒有輸出的檢查順序

```bash
ros2 node list
ros2 topic list -t
ros2 node info /processor
ros2 topic info /number
ros2 interface show std_msgs/msg/Int32
ros2 topic echo /number
ros2 topic echo /double
ros2 topic hz /number
```

`echo`、`hz` 會持續執行，完成觀察後按 Ctrl-C，再跑下一條，或使用另一個終端機。

| 要確認的事 | 指令與判讀 |
|---|---|
| 程式是否有建立 node | `node list` |
| 名稱與型別是否吻合 | `topic list -t`、`node info` |
| 是否有發送與接收端 | `topic info`；觀察工具也可能增加訂閱數 |
| 輸入真的有進來嗎 | `topic echo /number` |
| 處理後有送出嗎 | `topic echo /double` |
| 資料頻率如何 | `topic hz /number`；量到的是此訂閱端觀察到的頻率 |

停止隨機 publisher，保留 processor。在另一個終端機觀察輸出，再注入已知輸入：

```bash
ros2 topic pub --once /number std_msgs/msg/Int32 "{data: 21}"
```

原始 processor 預期輸出 42。先用小數值測試；Int32 的輸出也必須在型別範圍內。名稱、型別、程序都對仍不通時，再比對 QoS、`ROS_DOMAIN_ID` 與每個 shell 的 ROS 環境。

參考：[ROS 2 官方 Topic 教學](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Understanding-ROS2-Topics.rst)。

## C 編譯與錯誤定位

單檔範例可用：

```bash
cc -std=c11 -Wall -Wextra -O0 -g practice.c -o practice
./practice
```

pthread 原始範例依既有 Makefile 操作。一般 pthread 程式編譯需加入 `-pthread`；若使用特定 POSIX 擴充介面，還要遵守其 feature macro 要求。正式題目先使用題目提供的建置方式。

出錯先確認目前目錄、檔名、第一個編譯錯誤、輸入格式。執行結果錯時，縮小輸入並印出中間值；效能題先建立正確版本再量測。不要把額外除錯輸出混入要求嚴格格式的標準輸出。

## mask 與欄位替換

以下需 `#include <stdint.h>`，所有數值按 `uint32_t` 處理：

```c
/* bit n：0 <= n < 32 */
x |= UINT32_C(1) << n;          /* 設定 */
x &= ~(UINT32_C(1) << n);       /* 清除 */
x ^= UINT32_C(1) << n;          /* 反轉 */
uint32_t bit = (x >> n) & UINT32_C(1);

/* width：1..31；lo + width <= 32 */
uint32_t low_mask = (UINT32_C(1) << width) - UINT32_C(1);
uint32_t field = (x >> lo) & low_mask;
uint32_t mask = low_mask << lo;
uint32_t changed = (x & ~mask) | ((value & low_mask) << lo);
```

寬度為 32 的整欄位單獨處理：抽取結果就是 `x`、替換結果就是 `value`；不可執行 shift 32。若欄位不允許超範圍，應先檢查 value；上面的 mask 寫法會截掉多出的位元。

驗證三件事：抽取值正確、改後欄位正確、欄位外相同。最後一項可檢查 `(changed & ~mask) == (x & ~mask)`。

## byte 打包與解包

明確規定「第一個 byte 放最高位」，不依賴主機的記憶體排列：

```c
uint32_t word = ((uint32_t)b[0] << 24)
              | ((uint32_t)b[1] << 16)
              | ((uint32_t)b[2] << 8)
              | (uint32_t)b[3];
uint8_t high_byte = (uint8_t)(word >> 24);
uint8_t low_byte = (uint8_t)(word & UINT32_C(0xFF));
```

`b` 的元素型別為 `uint8_t`，至少有四個元素。`{0x12,0x34,0x56,0x78}` 應得到 `0x12345678`。

## 鎖與共享資料

- 列出所有共享物件，逐一指出誰會讀、誰會寫、靠什麼同步。
- 鎖包住完整讀改寫，不能只鎖讀取或只鎖寫回。
- `volatile` 不等於 atomic，也不是 thread 同步。
- 結果碰巧正確不能證明無鎖安全；單核心也可能出現交錯執行。
- 獨立計算放鎖外；多次量測後比較，確保改前改後輸出相同。

概念示意（省略初始化與錯誤處理）：

```c
local_result = independent_work();
pthread_mutex_lock(&mutex);
shared_total += local_result;
pthread_mutex_unlock(&mutex);
```

原 demo 的短鎖版本還有未同步的共享 `sink`，搬運引擎的 `busy` 也未正確同步；不要直接把這些細節當成安全同步範本。

## count 與搬運設定

```text
總 bytes = count × 每筆 bytes
claim → configure → start → wait → 檢查結果 → release
```

本練習 `engine.h` 的複製設定，需搭配 `<stdint.h>` 與 `engine.h`，並連結 `engine.c`：

```c
uint32_t src[100] = {0};
uint32_t dst[100] = {0};
engine_job_t job = {
    .src = src,
    .dst = dst,
    .count = 100,
    .size = XFER_32,
    .src_increment = true,
    .dst_increment = true,
};
int ch = engine_claim();
if (ch < 0) { /* 沒有可用通道：由呼叫端處理 */ }
else {
    engine_configure(ch, &job);
    engine_start(ch);
    engine_wait(ch);
    /* 在這裡驗證 dst 與 src 的 100 個元素相同 */
    engine_release(ch);
}
```

填值時來源改成指向一個同寬度 pattern，並將 `src_increment=false`。原始工作描述與 buffer 在工作完成前都要維持有效，且避免衝突存取。

正式硬體使用對應 SDK，別把這個模擬介面當成真實 API。查 [Pico SDK DMA 文件](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html#group_hardware_dma) 時優先找資料大小、讀／寫位址遞增、筆數編碼、啟動、完成與通道釋放。

## PIO 最小追蹤

```text
TX FIFO → OSR → out → X → in → ISR → push → RX FIFO
```

每一步都問：來源、目的、位元數、資料不足／FIFO 滿時的行為。Demo 假設 autopull 設定完成；實作時另外查移位方向、threshold、autopush 等設定。CPU 指令集與 PIO 指令集分開查。[官方 PIO API](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html#group_hardware_pio)

## 現場離線模型的提問模板

依現有規則筆記，現場模型沒有檔案上傳，且貼上與對話長度有限。一次只處理一個函式或一個錯誤；在考試期間使用現場指定模型。

```text
環境：語言、平台、SDK／ROS 版本（不知道的請標示未知）
目標：我想讓……
限制：必須維持的介面／不能使用的工具／時間與記憶體限制
相關程式：只貼最小相關片段，附必要型別與呼叫處
最小輸入：……
預期：……
實際：貼原始錯誤或輸出
已排除：……
請先指出兩個最可能原因與區分它們的檢查方法，
再給最小修改，以及一個正常與一個邊界測試。
不確定的 API 請明說，不要編造名稱。
```

卡在概念時：「請用這段程式中的實際變數，畫資料流／兩個執行緒時序。先不要改碼。」

需要 SDK 協助時：自己先找官方函式簽章，貼給模型；保留原有介面。模型給的碼要自己編譯、執行、比對，不把回答當成驗證結果。關鍵背景在新對話重新貼上，不依賴模型記住前面所有內容。

## 考場查找與提交

1. 找到題目的入口、輸入輸出規格、建置與提交方法。
2. 跑可工作的基準版本，保存原始輸出與耗時。
3. 一次改一件事，用同樣輸入驗證。
4. 先查自己的靜態筆記，再查官方 API，最後將具體問題交給指定模型。
5. 依現場規則提交並等待結果；根據實際錯誤改下一版。
