# 考場速查與本地模型提問

## 最常忘的規則

| 主題 | 直接查 |
|---|---|
| RV32I 欄位 | opcode=`w&0x7F`；rd=`(w>>7)&31`；funct3=`(w>>12)&7`；rs1=`(w>>15)&31`；rs2=`(w>>20)&31`；funct7=`(w>>25)&127` |
| 有號立即數 | I 格式取 bits31..20；12-bit 的0xFFC代表 -4，branch／store 另查格式 |
| 位址 vs 內容 | addi 只加值；lw 算 byte 位址後讀4 bytes；x0 固定為0 |
| 取欄位 | `(x >> shift) & low_mask` |
| 換欄位 | `mask=low_mask<<shift; x=(x&~mask)\|((value<<shift)&mask)` |
| 位元限制 | 用無號型別，32-bit 值不能移32位；~會翻轉整個型別的 bits |
| PIO 路徑 | CPU→TX FIFO→OSR→X→ISR→RX FIFO→CPU；out／in／push 對應中間三步 |
| FIFO 等待 | 輸入沒資料、輸出沒空間都可能等；push 不等於 CPU 已讀取 |
| ROS | node 是執行單位、topic 是通道；echo 只接收；/double 名稱不決定算法 |
| 共享資料 | 鎖保護完整讀改寫；volatile 不等於 atomic／同步 |
| buffer | queue 傳指標不複製內容；worker／DMA 用完前不能重用 |
| 搬運 | 總 bytes=count×每筆 bytes；複製兩端遞增，填值來源固定 |
| count vs memcpy | DMA／演練 count 是筆數；memcpy 第三參數是 bytes |
| 校驗 | CRC 要核對版本、初值、反射、最後 XOR、資料範圍；完成後讀 sniffer |
| 多板 | 按 job_id 對回輸入，不能把分類編號相加 |
| 改了沒變 | 存檔→確認同一份→重新建置→重啟／寫入板子 |
| 慢在哪 | 量整條路各段，非同步工作等完成才停表 |

本 repo 的 processor 是3*x+1（21→64）、搬運 N=8；官方原式2*x（21→42）、N=4096。

## 卡住時的順序

**收到輸入 → 解析 → 計算／分派 → 等完成 → 包裝 → 回傳。** 每段查型別、數量、單位、誰讀寫。固定錯先查規格，偶爾錯先查越界／同步／buffer。

## 用26B等本地模型：一次完成一個能核對的小任務

**資料由題目／文件提供，模型幫你解讀與修改，編譯器和實際輸出負責驗證。** 參數量不能單獨決定能不能解這題；先用熟悉的例子看它有沒有讀懂規格，再決定交給它多大的工作。

### 你不會切題，也能先這樣問

```text
下面是題目相關的一段：
[貼需求與提供的程式介面]

先不要寫完整程式。
請列出輸入、輸出、限制，將「文件已寫明」與「仍需查明」分開。
把這一段拆成最多3個小步，每步列出要改的位置與怎樣驗證。
缺資料時，指出要我補哪個函式／型別宣告，或去文件查什麼關鍵字。
```

先核對它有沒有讀錯型別、單位、正負或輸出順序。連規格都錯，就先修正這一層，不接著產生大量程式。

### 每次貼這五樣

| 貼什麼 | 怎樣才夠用 |
|---|---|
| 題目依據 | 只貼這一步有關的規格，不叫它自行讀整份 GitHub |
| 環境與介面 | 實際板型／SDK／ROS版本，相關函式宣告、typedef、enum |
| 目前程式 | 一個函式，加必要呼叫處與型別；不要硬截掉依賴 |
| 一組已知答案 | 輸入、預期輸出與長度單位；邊界條件按題目補 |
| 唯一任務 | 解釋、找錯、修改、量測，每次選一個 |

模型若只接受貼文字，就從筆記／官方文件複製相關片段，貼內容而非只貼連結。**貼真實宣告，比叫它憑記憶寫一套 SDK 更容易核對。**

### 最常用：只改一個函式

```text
環境／版本：
題目規格：
實際 API／型別宣告：
目前函式與相關呼叫：
已知輸入→預期輸出：
實際結果：

本輪只修正：[唯一問題]
沿用現有介面與資料格式，給最小修改及必要 include。
指出改哪幾行、原因，以及上面輸入應得到什麼。
若缺少關鍵宣告，先問我要；不要猜 API 或改整個架構。
```

模型給修改後，先看差異，再建置／執行。要求「最小修改」只是縮小檢查範圍，**不會保證它一定答對**。

### 編譯失敗、算錯、變慢，分開問

| 發生什麼 | 貼回什麼／這輪問什麼 |
|---|---|
| 編譯失敗 | 實際建置命令、第一個錯誤的完整相關段落、對應宣告；問是編譯／連結／工具鏈哪一層 |
| 輸出錯誤 | 一筆輸入、預期、實際、目前函式；問第一個與規格不符的位置 |
| 偶爾錯 | buffer由誰讀寫、生命週期、完成條件與發生錯誤的例子；問共享存取是否同步 |
| 答案對但慢 | 各段實測時間、工作量、編譯設定；只問最慢一段的改法 |

模型沒有執行你的環境；它說「測試通過」不算證據。真正要看的是你執行後的結果。若連續修改仍卡在同一錯誤，停止堆補丁，回頭補實際宣告／縮小出錯範圍。

### 可直接貼的例子：你問過的搬運

```text
這是演練自訂 engine，不是 Pico SDK。
已知規格：count 是傳輸筆數；XFER_32 是每筆4 bytes。
預定搬 N=8 筆；示範陣列實際預留32筆。
目前設定：
job.size = XFER_32;
job.count = N * sizeof(uint32_t);

只回答三點：現在搬幾 bytes、超出預定幾筆、count 那行應怎麼改。
區分「超出預定範圍」與「超出實際配置」，不要新增 API。
```

**你可核對的答案：**32筆×4＝128 bytes，比預定多24筆；應改 `job.count=N`。此 demo 預留32筆，沒有因此超出實際配置；若真的只配8筆才會越界。

PIO 也可用同樣問法：給 OSR=21、X=7、autopull與autopush關閉、RX有空間，再貼 `out y,32`／`in x,32`／`push`，問每步的來源與目的。答案應是7，因為讀了舊X；詳見 [PIO回顧](demo操作回顧.md#例題05pio-資料)。

### 對話變長：帶已確認事實開新對話

介面支援新對話／重設上下文時，用這張摘要接力；不要搬整段聊天或把模型猜測當事實。關鍵程式與宣告仍要重貼：

```text
目前唯一目標：
環境／板型／版本：
已從題目確認的規格：
已套用的修改：
已實際驗證的輸入→結果：
目前程式與必要宣告：
仍失敗的例子／原始錯誤：
本輪只要解決：
```

可以請模型草擬摘要，但自己核對後才帶走。不能把「它認為已修好」寫成「已驗證」。

### 最值得交給模型的工作

**讀一段規格、翻譯一個函式、依現成 API 補一小段、根據錯誤修一處。** ISA要求列欄位／有號值／位址；PIO要求列資料流／等待條件；DMA要求列筆數／寬度／bytes；平行要求列誰讀寫同一份資料。

這些策略不需要外掛、API或模型自己上網。考場只用指定的本地介面，規則見 [考場規定](成大上機考規則與避雷.md)。

方法依據：[將複雜任務拆成小提示](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/prompts/break-down-prompts)、[明確指示與示例](https://docs.mistral.ai/resources/cookbooks/mistral-prompting-prompting_capabilities)。這裡把方法套到本 repo，並非對未知考場模型的實測保證。
