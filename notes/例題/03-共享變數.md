# 03 為什麼加兩次，最後只有 1

[← 回考場筆記入口](../README.md) · [舊練習索引](../舊練習索引.md)

> 舊例題留存：這頁保留當時的修改任務。查概念與指令請用 [技術手冊](../技術/README.md)。


對照原附檔 [critical-section/main.c](../../demo/section2-3/critical-section/main.c)。先用一支沒有 thread 的小程式，把交錯過程固定重演。

## 原版：兩邊都先拿到舊值

新增自己的 `counter_steps.c`：

```c
#include <stdio.h>

int main(void) {
    int counter = 0;
    int a = counter;      // 模擬 A 先讀到 0
    int b = counter;      // 模擬 B 也先讀到 0
    counter = a + 1;      // A 算完，寫回 1
    counter = b + 1;      // B 用自己的舊值，還是寫回 1
    printf("%d\n", counter);
    return 0;
}
```

```bash
cc counter_steps.c -o counter_steps
./counter_steps
```

輸出 **1**。a、b 存的是讀取當下的值；counter 後來改變，不會讓 a、b 自動跟著更新。

## 改一次：等 A 寫完，B 才讀

只把 `int b = counter;` 移到 A 寫回之後：

```c
int counter = 0;
int a = counter;
counter = a + 1;      // counter 已經是 1
int b = counter;     // B 現在讀到 1
counter = b + 1;      // 寫回 2
```

重編譯，輸出變成 **2**。

**同樣做兩次加一，只改讀寫順序，結果就不同。**

## 接回原附檔

原附檔的兩個 worker 共享 counter；無鎖版本沒有保證讀寫順序。鎖的作用，是讓其他合作使用同一把鎖的 worker 等完整更新結束：

```text
A：lock → 讀 → 加一 → 寫回 → unlock
B：                               lock → 讀新值 → 加一 → 寫回
```

在 `/demo/section2-3` 執行：

```bash
make run-critical-section
```

只先看：第二、三種版本都把 counter 的更新放進鎖裡；第三種還把耗時工作放進鎖，別人要等更久。

無鎖版本的數字不能預先保證；C 的 data race 會造成未定義行為。上面的小程式只是固定重演一種順序，沒有實際建立 thread。原範例另有共享 sink 的同步問題，詳見 [補充](../底層架構與資料流.md)。

## 換你試

在第一版加上 `int c = counter;`，讓 a、b、c 都先讀到 0，再依序寫回各自的「舊值 + 1」。最後是多少？

<details>
<summary>看答案</summary>

仍然是 **1**。要得到 3，必須每次都在上一次寫回後，才讀取新值。

</details>

**過關：**能用 a、b 的實際數值說明，為什麼鎖要包住完整的讀、改、寫。
