# 底層架構與資料流

目標是看到新程式時，先辨認「誰執行、資料在哪裡、什麼時候可以讀」。先理解下面三張圖，再回到對應 demo。

## 一 CPU 暫存器與記憶體

```text
記憶體中的程式指令 → CPU 取指、解碼、執行
                         │
記憶體中的資料 ← load/store → CPU 暫存器 → 算術與位元運算
```

暫存器是 CPU 執行指令時使用的小型儲存空間；記憶體則存放程式與資料。C 的變數是語言層的概念，編譯器決定如何映射到暫存器或記憶體，不能假設每一個變數永遠對應固定的硬體暫存器。

`uint32_t x = 0xA5` 中，`x` 的值是整數；`&x` 是它所在的位址；`*p` 則依指標型別讀取或寫入指向的物件。不要把位址數值和物件內容混在一起。

`uint32_t a[100]` 有 100 個元素，共 400 bytes（本練習環境每 byte 為 8 bits）。若 `uint32_t *p = a`，`p + 1` 指向下一個元素，位址前進 4 bytes。`sizeof(a)` 是整個陣列的 bytes；`sizeof(p)` 是指標本身大小。在函式參數中的 `uint32_t a[]` 會調整為指標，不能用 `sizeof(a)` 算出呼叫者的陣列長度。

### 位元欄位不是記憶體位址

一個整數可以包含多個欄位。欄位規格說 bits 7..4，就是同一個值中的四個位元，取法是先右移到最低位，再遮罩。

```c
uint32_t field = (x >> 4) & UINT32_C(0xF);
uint32_t changed = (x & ~UINT32_C(0xF0))
                 | ((value & UINT32_C(0xF)) << 4);
```

第一部分清空原欄位；第二部分放入新欄位。只用 OR 放入值，無法把原本的 1 清成 0。

### 位元順序與 byte order

`0x12345678` 是數值。若你明確寫 `(b0 << 24) | (b1 << 16) | ...`，是在規定哪個輸入 byte 放進哪個數值欄位。Endianness 描述多 byte 值在記憶體中的 byte 排列；它不會改變整數運算中 `x >> 24` 的意義。

在 C 中先把 byte 轉成 `uint32_t` 再做大幅左移，避免整數提升後以 signed 型別運算造成問題。移位數必須小於被移位型別的位元寬度；`1u << 32` 不能拿來建立常見 32-bit unsigned int 的全位元遮罩。

## 二 ROS 2 是程式之間的通訊

```text
publisher.py 程序                         processor.py 程序
  timer callback                          訂閱 callback
     │                                          │
     └─ publish Int32 → /number → 接收 Int32 → 乘 2
                                                │
                                     /double ← publish Int32
                                                │
                                          ros2 topic echo
```

這份 demo 每個 Python 程序各建一個 node。一般情況不必是一個程序對應一個 node。Topic 是有名稱、訊息型別的通訊介面；不要把它當成保存最後一個值的普通共享變數。

`create_timer(1.0, ...)` 建立週期工作；`create_subscription(...)` 登記接收時的 callback；`rclpy.spin(node)` 讓 executor 處理可執行的工作，例如計時器與收到的訊息。Callback 需要被執行，計算才會發生。

`ros2 topic echo` 會參與通訊並建立訂閱者，因此觀察工具可能改變你看到的 subscriber 數。Topic 存在也可能只是因為訂閱者仍在，不能據此判定資料正在流動。[官方 Topic 教學](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Understanding-ROS2-Topics.rst)

初步除錯先找 node 與連線，再查資料。若兩端都存在、名稱與型別一致仍不通，再看 QoS、ROS domain 與環境設定。先處理可觀察到的最小問題。

## 三 CPU PIO 與 DMA 分工

```text
CPU：執行一般程式，設定周邊與處理結果
 │
 ├─ PIO state machine：執行 PIO 小程式，處理輸入輸出與移位
 │      CPU → TX FIFO → OSR → out → X
 │                                  │
 │      CPU ← RX FIFO ← push ← ISR ← in
 │
 └─ DMA：依設定搬資料
        來源位址 → 一筆一筆傳輸 → 目的位址
```

PIO 和 DMA 都是周邊功能，工作方式不同。PIO 有自己的指令與狀態機；DMA 主要依設定搬資料。CPU 的指令集（例如 RISC-V）與 PIO 指令集也不同，不能將兩種組語混用。

### 逐步讀 PIO demo

範例前提是 OSR 啟用 autopull，並有適當的狀態機、FIFO 與移位設定；本 repository 的 `.pio` 只供閱讀，沒有完整的主機設定程式。

| 指令或設定 | 資料方向 | 要問的事 |
|---|---|---|
| autopull | TX FIFO → OSR | 資料不足時，狀態機會不會等待？ |
| `out x, 32` | OSR → X | 取出多少位元？目的暫存器是誰？ |
| `in x, 32` | X → ISR | 資料如何累積到輸入移位暫存器？ |
| `push` | ISR → RX FIFO | FIFO 沒空間時如何處理？ |
| `.wrap` | 回到迴圈起點 | 這裡是彙編器的 wrap 標記，不是一筆額外執行的跳躍指令 |

`out` 是從 OSR 輸出到指定目的，`in` 是將指定來源輸入 ISR；不要直接解讀成「CPU 送出／CPU 收到」。FIFO 用來暫存資料，但容量有限；等待或阻塞也是資料流的一部分。更多設定可查 [Pico SDK PIO API](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html#group_hardware_pio)。

### 指令編碼練習

以下是練習用的假想格式，不是實際 RISC-V 或 PIO 編碼：

```text
16-bit word
bits 15..12：op（4 bits）
bits 11..8 ：reg（4 bits）
bits 7..0  ：imm（8 bits）
```

讀取 `0xA35C`：`op=0xA`、`reg=3`、`imm=0x5C`。編碼 `op=2, reg=5, imm=0xAB`：結果 `0x25AB`。無論題目換成指令或封包，做法都是先依規格標欄位，再抽取或打包。真正的指令可能把 immediate 分散在多段欄位，也可能需要符號延伸，必須看實際欄位圖。

## 四 執行緒與共享資料

```text
thread A：自己的執行位置、暫存器、stack ─┐
                                       ├→ 同一程序的共享記憶體
thread B：自己的執行位置、暫存器、stack ─┘        counter、sink
```

兩個 thread 可存取同一個全域變數。即使一個加法在 C 只寫一行，也不代表整個讀改寫具備原子性。

| 時間 | thread A | thread B |
|---|---|---|
| 1 | 讀到 counter=0 | |
| 2 | | 讀到 counter=0 |
| 3 | 寫回 1 | |
| 4 | | 寫回 1 |

這張圖用來理解 lost update。以 C 的記憶體模型來說，未同步的衝突存取若至少有一次寫入，就可能形成 data race，行為未定義；不能用某次結果推斷它總會如何執行。

鎖要包住完整的「讀 → 計算新值 → 寫回」。如果計算不依賴共享資料，先在鎖外算，再鎖住必要更新，可減少互相等待。Spinlock 在等待時反覆檢查；mutex 等待可能讓執行緒阻塞，選擇取決於環境與持鎖時間。不要只憑單次跑分判定優劣。

`volatile` 不提供互斥、原子性或執行緒之間的同步。跨 thread 的旗標需要正確的 atomic 或鎖；`pthread_join` 可用來等待該 thread 結束。更多 mutex 語意可查 [POSIX mutex 規格](https://pubs.opengroup.org/onlinepubs/9799919799/functions/pthread_mutex_lock.html)。

### 閱讀這份 demo 時要分清的事

- 無鎖 `counter` 是故意展示問題，結果可能不正確，也可能碰巧等於預期。
- `sink += work(i)` 在短鎖版本仍是共享資料的未同步更新。因此 counter 有鎖，不代表整支程式已排除所有 data race。
- 搬運引擎的 `busy` 是 `volatile bool`，工作 thread 與主 thread 的讀寫沒有正確同步。它能展示介面節奏，但不能作為正式執行緒同步寫法的範本。
- 這些限制來自現有原始碼；準備時先學會辨識，若實作自己的同步練習，可使用 mutex 或標準 atomic，並處理 thread 建立失敗。

## 五 資料搬運與 DMA

```text
claim → configure → start → 等待完成 → 使用結果 → release
```

CPU 描述從哪裡讀、往哪裡寫、搬幾筆、每筆幾 bytes、位址是否遞增。啟動成功代表工作開始，使用結果前仍要確認完成。

| 工作 | 來源遞增 | 目的遞增 | 結果 |
|---|---|---|---|
| 陣列複製 | 是 | 是 | 依序讀來源、寫目的 |
| 固定值填滿陣列 | 否 | 是 | 反覆讀同一值、依序寫目的 |

總 bytes＝傳輸筆數 × 每筆 bytes。100 筆 32-bit 值是 400 bytes，count 仍是 100。真實硬體的 count 欄位還可能有模式編碼；例如 RP2350 的 transfer count 有額外編碼規則，使用時依 SDK 文件，不直接把 demo struct 套過去。[官方 DMA API](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html#group_hardware_dma)

搬運期間來源與目的 buffer 必須持續有效；不要提早離開來源區域變數的生命週期、釋放記憶體，或同時修改正被搬運的資料。讀取結果前等待完成，也要遵守平台的記憶體可見性要求。

本 demo 用 pthread 執行搬運，仍消耗 CPU 執行時間。真正 DMA 能把搬運工作交給硬體，但仍有設定、同步、匯流排與記憶體頻寬成本，並非完全沒有成本。

## 六 看到新題目時先畫什麼

先寫六項：輸入在哪裡、輸出在哪裡、由誰執行、哪些資料共享、何時算完成、以什麼測試判定正確。若有優化要求，先保留可驗證的基準版本，再改一件事並比較同樣輸入的輸出與耗時。
