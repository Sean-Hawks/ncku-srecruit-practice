# 底層架構與資料流

**只追三件事：資料放哪裡、誰處理、何時完成。**

從你接觸過的 Web 事件、程式與 CLI 切入；每節讀完就做一題。

## 1 CPU 怎麼操作資料

程式裡的運算，最後要由 CPU 執行指令：

```text
記憶體 → 讀到暫存器 → 運算 → 寫回記憶體
```

暫存器是 CPU 執行指令時使用的小型儲存空間。C 變數怎麼放進暫存器或記憶體，由編譯器決定。

`x` 是值，`&x` 是位址，`*p` 是指標指向的物件。這三個先分開。

**動手：**宣告 `uint32_t a[100]`、`uint32_t *p=a`。解釋 `p+1`：它前進一個元素，在本環境就是 4 bytes。

<details>
<summary>常忘的 sizeof 與 byte order</summary>

- 此陣列有 100 個元素、400 bytes；`sizeof(a)` 是陣列大小，`sizeof(p)` 是指標大小。
- 函式參數 `uint32_t a[]` 會調整成指標，不能在函式裡靠 `sizeof(a)` 得到原陣列長度。
- Endianness 是多 byte 值在記憶體裡的排列；`x >> 24` 永遠是在數值裡取高位，不會因記憶體排列而改變意義。

</details>

## 2 為什麼需要位元運算

Web 物件靠欄位名稱區分資料：

```js
{ mode: 3, enabled: true }
```

硬體介面或封包可以把欄位塞進同一個整數；規格用「第幾個 bit」標位置。你要自己抽取、替換。

```text
0xD6 = 1101 0110
       高四位 低四位
```

```c
uint32_t x = 0xD6u;
uint32_t mode = (x >> 4) & 0xFu;       // 13
uint32_t changed = (x & ~0xF0u)
                 | ((3u & 0xFu) << 4); // 0x36
```

右移把目標移到最低位；AND 清掉不要的位元。替換時先清空原欄位，再放入新值。只用 OR 無法把原本的 1 清成 0。

**動手：**把 `0xA5` 的 bits 5..2 改成 3。除了算答案，還要確認其他位元沒變。

<details>
<summary>延伸：指令也可以是欄位</summary>

假想 16-bit 指令：bits 15..12 是 op、11..8 是 reg、7..0 是 imm。`0xA35C` 就可拆成 `op=10、reg=3、imm=92`。

這是假想格式。真正的 RISC-V 指令按實際欄位圖解析，immediate 可能分散且需要符號延伸。`demo_asm.c` 本身是 C 位元運算範例。

</details>

## 3 ROS 2 為什麼需要 topic

兩個獨立程式各有自己的狀態；要交換資料，就需要通訊介面。可先用事件訂閱理解：

```text
publisher → /number → processor 的 callback → /double → echo
```

Topic 是具名稱與訊息型別的通道。訂閱登記 callback；`rclpy.spin` 讓 executor 處理訊息、timer 等工作。

因此「程式存在、接線正確、有資料、callback 執行」要分別確認。Topic 存在不能證明有人發送；`echo` 自己也會建立訂閱者。

**動手：**停掉隨機 publisher，CLI 發送 21，原版應輸出 42。再把訂閱改成 `/numbers`，沿資料流查出斷點。

[官方 Topic 教學](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Tutorials/Beginner-CLI-Tools/Understanding-ROS2-Topics/Understanding-ROS2-Topics.rst)

## 4 PIO 為什麼有自己的指令

固定的輸入輸出流程也需要執行者。PIO 提供小型狀態機，依自己的指令處理資料，CPU 負責設定與收送。

範例假設 autopull 與狀態機設定已完成：

```text
CPU → TX FIFO → OSR → X → ISR → RX FIFO → CPU
```

| 動作 | 資料移動 |
|---|---|
| autopull | TX FIFO → OSR |
| `out x, 32` | OSR → X，32 bits |
| `in x, 32` | X → ISR，32 bits |
| `push` | ISR → RX FIFO |

FIFO 是有限容量的緩衝區。沒有輸入、輸出沒空間，都可能讓流程等待；行為要連同指令與設定一起看。CPU 指令集與 PIO 指令集分開查。

**動手：**假設送入 `0x12345678`，逐步指出資料在哪裡；再問「CPU 不送下一筆時，哪一步會等？」

[官方 PIO API](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html#group_hardware_pio)

## 5 為什麼加一需要鎖

同一程序的 thread 可以存取同一個共享物件。`counter++` 的讀改寫，可能與另一個 thread 交錯：

```text
A 讀到 0 → B 讀到 0 → A 寫回 1 → B 寫回 1
```

所以鎖要包住完整的「讀 → 改 → 寫」。只鎖寫入，前面讀到的值仍可能過期。獨立計算放鎖外，可縮短別人等待的時間。

這是理解 lost update 的時序。C 的未同步衝突存取可能構成 data race、造成未定義行為，不能保證每次出現哪個數字。`volatile` 也不提供原子性或 thread 同步。

**動手：**在 demo 標出 `counter、sink、lock`，逐一回答誰會讀寫、靠什麼同步；再比較短鎖與長鎖的耗時。

<details>
<summary>原始 demo 的兩個額外問題</summary>

- 短鎖版本的 `sink += work(i)` 仍有未同步的共享更新。
- 搬運引擎的 `busy` 是 `volatile bool`，跨 thread 讀寫缺乏同步。

因此範例可以用來理解概念，正式同步寫法要使用正確的鎖或 atomic；跑對一次不代表安全。

</details>

## 6 為什麼 DMA 要填那些欄位

CPU 寫複製迴圈，需要自己執行讀寫。DMA 用專用硬體執行搬運；要完成同樣的工作，就得知道：

```text
從哪讀 → 往哪寫 → 幾筆 → 每筆多大 → 位址要不要前進
```

100 個 `uint32_t`＝100 筆 × 4 bytes＝400 bytes。`count` 填 100。

| 工作 | 來源位址 | 目的位址 |
|---|---|---|
| 複製陣列 | 每筆前進 | 每筆前進 |
| 固定值填滿 | 留在 pattern | 每筆前進 |

啟動只是開始，所以流程是：

```text
claim → configure → start → wait → 驗證 → release
```

來源與目的 buffer 在完成前要維持有效，避免衝突存取，並滿足對齊要求。Demo 用 thread 模擬搬運，仍消耗 CPU；硬體 DMA 也有設定與頻寬成本。

**動手：**設定 100 筆複製，再只改來源與遞增設定，完成 100 筆填值。等待後逐筆檢查。

[官方 DMA API](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html#group_hardware_dma)：真實 SDK 的筆數可能含模式編碼，依實際規格填寫。
