# 架構與 C 記憶體

[← 回考場入口](README.md)

**先問：誰執行？資料在哪？用什麼方法交給下一段？**

## 各項技術扮演什麼角色

| 名詞 | 是什麼／做什麼 |
|---|---|
| CPU 核心 | 執行指令的硬體，讀值、計算、寫結果 |
| 暫存器 | 執行者旁的小型儲存位置，暫放值與位址 |
| RAM | 放陣列、封包、模型、共享變數的記憶體 |
| ISA | 規定機器碼每個欄位與執行效果 |
| PIO | 執行自己短指令的周邊，處理接腳時序／位元流 |
| FIFO | 有限容量、先進先出的資料佇列 |
| DMA | 按來源、目的、筆數與寬度搬資料的硬體 |
| ROS 2 | 用具名稱、型別的 topic 讓程式交換訊息 |
| Docker | 給程序指定套件、路徑與執行環境 |

## 三條資料路徑

```text
CPU：RAM 輸入 → 讀到暫存器 → 執行指令 → 寫結果
ROS：publisher → topic → callback 處理 → topic → 接收者
PIO：CPU → TX FIFO → OSR → X → ISR → RX FIFO → CPU
```

ROS topic 不替你運算；PIO push 只把結果放到 RX FIFO，CPU 還要讀；DMA start 只是開始，完成後才能取結果。它們分工不同。

## C：值、位址與長度

假設位址 0x1008 裡存 42：**0x1008 回答「在哪」，42 回答「裡面是什麼」。** 加出位址不代表已讀內容。

| 寫法 | 意思 |
|---|---|
| `x` | 變數的值 |
| `&x` | x 的位址 |
| `p` | 指標裡存的位址 |
| `*p`／`p[i]` | 該位址的物件／第 i 個元素，p[i] 等同 *(p+i) |
| `p = src` | 複製位址，沒有複製內容 |
| `memcpy(dst, src, bytes)` | 複製內容；第三參數是 bytes，區域不能重疊 |

memcpy 需 `<string.h>`；重疊用 memmove，兩者都不替你檢查容量。C 陣列宣告後不能用 dst=src 整體賦值。

在本環境，1 byte=8 bits；uint32_t=32 bits，所以 sizeof(uint32_t)=4 bytes。

| 假設 `uint32_t a[3]` | 結果 |
|---|---|
| sizeof(a) | 12 bytes |
| sizeof(a[0]) | 4 bytes |
| a+1 | 前進一個元素，即4 bytes |
| sizeof(p)，p 是指標 | 指標本身大小，看平台，不是資料長度 |

函式參數的陣列會調整成指標，不能在函式裡用 sizeof(a) 推回原陣列長度，要另外傳 count。

## 為什麼改 p 會動到 src

```c
uint32_t src[2] = {10, 20};
uint32_t *p = src;
uint32_t dst[2];
memcpy(dst, src, sizeof src); // dst 是另一份內容
p[0] = 99;
// src[0]=99；dst[0] 仍是10
```

struct 裡若含指標，複製 struct 仍指向同一個 buffer，不會自動深層複製內容。queue 傳指標也一樣。

## 最需要查的記憶體錯誤

| 問題 | 原因 |
|---|---|
| a[8]，但陣列只有8格 | 索引只能0..7 |
| 回傳區域陣列的位址 | 函式結束後物件失效 |
| worker／DMA 還沒用完就重用 buffer | 正在讀寫的資料被覆蓋 |
| 把任意 byte buffer 轉 uint32_t* 讀 | 需符合長度、對齊、型別存取規則 |
| 把 8 筆當8 bytes | 還要乘每筆寬度，uint32_t 的8筆是32 bytes |

## 陌生程式怎麼追

```text
從哪收到 → 放進哪個 buffer → 誰處理 → 何時完成 → 往哪交答案
```

每段查 **型別、數量、單位、誰讀寫**。同一程序的 thread 可共享 RAM；不同板子各有 RAM，要透過通訊交接，不能拿指標直接讀另一塊板。
